PANDUAN PROYEK · JOBSHEET 1–12

Apa yang dilakukan kode di setiap Jobsheet?

Proyek ini berkembang dari halaman perpustakaan statis, menjadi halaman interaktif, lalu menjadi aplikasi PHP yang menyimpan data dan transaksi di PostgreSQL. Bagian di bawah menjelaskan fungsi berkas yang tersedia dan perubahan penting di setiap tahap.

Perubahan mulai Jobsheet 8

Jobsheet 1–7 berlatih membangun SIMPUS (perpustakaan mini). Mulai Jobsheet 8, proyek beralih ke aplikasi inventaris dan penjualan: barang, pelanggan, stok, serta arus kas disimpan di PostgreSQL melalui PHP PDO. Jobsheet 9 melengkapi CRUD; Jobsheet 10–11 menambahkan login dan perlindungan request; Jobsheet 12 merelasikan transaksi ke barang/pelanggan dan memperkuat alur pembelian. Penjelasan di handbook ini mencakup tujuan, susunan berkas, alur, dan cara menguji tiap tahap. Buka repositori GitHub untuk melihat seluruh kode proyek.

Pola umum file dan alurnya

  • index.html atau index.php adalah halaman beranda. HTML menyusun judul, menu, konten, tabel, dan formulir. PHP pada beranda yang lebih baru juga dapat mengambil data untuk ringkasan dashboard.
  • Folder buku/, anggota/, barang/, dan pelanggan/ memisahkan halaman menurut jenis data. list menampilkan tabel, tambah/edit menampilkan formulir, sedangkan proses_tambah, proses_edit, proses_beli, dan sejenisnya menerima kiriman formulir lalu mengubah data.
  • assets/css/style.css mengatur warna, ukuran, tata letak, tabel, formulir, dan tampilan layar kecil. File JavaScript di assets/js/ menambahkan respons pada klik, pencarian, pemuatan data, atau validasi formulir.
  • includes/header.php dan footer.php adalah potongan tata letak bersama yang disisipkan di banyak halaman agar menu, tautan CSS/JavaScript, dan footer konsisten. koneksi.php menyiapkan koneksi basis data PDO.
  • File .json berisi contoh data berbentuk JSON; file .sql berisi perintah untuk membuat tabel basis data. README, wireframe, dan infografis adalah dokumentasi, bukan instruksi yang dijalankan aplikasi.

Alur data aplikasi PHP: pengguna mengirim form dengan POST → handler memeriksa input → data disimpan/diubah di session atau database → pesan sementara disimpan di session → browser diarahkan kembali ke halaman daftar. Tautan GET umumnya dipakai untuk membuka halaman atau memilih data berdasarkan ID.

Fungsi folder api/ dan vercel.json

Di root proyek, folder api/ hanya berisi index.php. File ini berperan sebagai front controller/router untuk deployment: membaca path request, mencari file yang diminta di root proyek, memilih index.html atau index.php jika path berupa folder, menyajikan HTML/CSS/JavaScript dengan content type, dan menjalankan file PHP melalui require. Jika file tidak ditemukan atau ekstensi tidak ditangani, router mengembalikan HTTP 404. Ini bukan kumpulan endpoint bisnis yang mengembalikan JSON.

File vercel.json menunjuk runtime vercel-php@0.9.0 untuk api/index.php, lalu menerapkan dua aturan secara berurutan: request /assets/... diteruskan langsung ke asset yang cocok; request lainnya diteruskan ke /api/index.php. Router kemudian mencari halaman Jobsheet atau file proyek berdasarkan URL yang diminta.

1 · BrowserMengirim request, misalnya URL halaman Jobsheet atau stylesheet.
2 · VercelMemilih runtime PHP dan menerapkan aturan route dalam vercel.json.
3 · Router PHPapi/index.php mencari file tujuan, mengeksekusi PHP atau menyajikan file statis, atau mengembalikan 404.

Konfigurasi ini tidak menetapkan CORS, security headers, atau environment variable. Nilai koneksi database perlu disetel pada environment deployment jika halaman yang dijalankan membutuhkannya. Lingkungan Laragon/XAMPP lokal biasanya menyajikan file secara langsung dan tidak menggunakan front controller Vercel.

Cara kerja CSS — mengubah aturan menjadi tampilan

CSS (Cascading Style Sheets) tidak mengubah isi data. Ia memberi aturan visual kepada elemen HTML. Browser memuat HTML, membaca aturan CSS yang dirujuk lewat <link rel="stylesheet"> atau tag <style>, mencocokkan selector, lalu menghitung aturan mana yang menang sebelum menggambar halaman.

1. Selector memilih elemen

  • body memilih elemen body; header nav a memilih tautan yang berada di dalam nav dalam header.
  • .btn-theme memilih elemen dengan class tersebut. Satu elemen dapat mempunyai beberapa class Bootstrap dan class proyek sekaligus.
  • #navMenu memilih elemen dengan id itu. Id seharusnya unik dalam satu halaman.
  • :hover dan :focus adalah pseudo-class: aturan berlaku saat kursor berada di elemen atau elemen menerima fokus keyboard.

2. Deklarasi berisi properti dan nilai

.btn-theme {
    background-color: var(--primary-color, #5c3d2e);
    color: #fff;
    padding: .65rem 1.5rem;
}
.btn-theme:hover {
    background-color: var(--primary-hover, #43281c);
}

Nama sebelum kurung kurawal adalah selector. Setiap baris di dalamnya adalah deklarasi: properti seperti color atau padding diberi nilai. Contoh memakai warna mocha dan cokelat tua yang sesuai tema saat ini; aturan :hover mengganti warna saat pointer berada di atas tombol.

3. Cascade, class, dan Bootstrap

Jika beberapa aturan mengatur properti yang sama, browser menerapkan cascade: prioritas asal/important, kekhususan selector (specificity), lalu urutan aturan bila kekhususannya setara. Karena jobsheet memuat Bootstrap dan CSS proyek, aturan khusus proyek biasanya diletakkan setelah Bootstrap agar dapat menimpa gaya dasarnya. Inline style pada atribut style cenderung lebih kuat dari selector biasa; hindari !important kecuali memang dibutuhkan.

4. Box model dan tata letak

Setiap elemen dapat dipahami sebagai kotak: content (isi), padding (ruang di dalam), border (garis), dan margin (jarak luar). Aturan * { box-sizing: border-box; } membuat ukuran yang ditetapkan sudah menghitung padding dan border. Flexbox cocok untuk menyusun item satu arah; Grid cocok untuk baris/kolom; class Bootstrap seperti container, row, dan col-md-4 menyediakan pola layout siap pakai.

5. Responsive dan perubahan tema

Media query seperti @media (max-width: 760px) mengaktifkan aturan hanya pada layar yang lebih sempit. Jobsheet awal memakai aturan CSS dasar; tahap berikut memanfaatkan grid/responsive Bootstrap, dan stylesheet yang lebih baru menggunakan breakpoint. Custom property seperti --primary-color dan --dark-chocolate di :root menyimpan warna yang dipakai ulang, misalnya color: var(--primary-color). Jika tampilan tidak berubah, periksa alamat CSS pada href, selector/class pada HTML, urutan stylesheet, dan cache browser.

6. Komponen antarmuka yang ditata CSS

Di Jobsheet awal CSS memberi gaya langsung pada elemen semantik seperti header, nav, main, tabel, form, dan footer. Jobsheet yang memuat Bootstrap memakai class utilitas/komponen seperti container, row, col-*, card, btn, table, alert, dan form-control. CSS proyek kemudian mengatur ulang tema cokelat-krem, navbar gelap, tombol, kartu statistik, tabel, jarak, radius, bayangan, serta status stok. Prefix bg-, text-, d-, gap-, dan p-/m- yang terlihat pada markup biasanya merupakan utilitas Bootstrap untuk warna, display, jarak, padding, dan margin.

7. Status, interaksi, dan layout yang responsif

CSS mengatur tampilan status seperti stok habis/menipis/tersedia, tombol hover/focus, pesan, menu aktif, tabel yang dapat digulir, modal, dan tombol autentikasi. Flexbox menyusun navbar dan aksi; grid Bootstrap menyusun kartu dashboard dan kolom form. Breakpoint menyusun ulang elemen untuk layar sempit. Pada beberapa halaman, navbar dikendalikan oleh Bootstrap JavaScript, sedangkan pola checkbox/CSS di Jobsheet 4 membuka menu tanpa kode JavaScript khusus. Elemen HTML seperti table-responsive atau modal tetap memerlukan class dan markup yang sesuai; CSS sendiri tidak mengambil atau menyimpan data.

8. Cara menelusuri aturan gaya

Mulai dari elemen yang tampil, catat class/id-nya, lalu cari selector terkait di assets/css/style.css. Periksa apakah Bootstrap dimuat sebelum CSS proyek, apakah ada inline style, serta aturan hover/focus dan media query. Beberapa halaman memuat font melalui Google Fonts dan Bootstrap melalui CDN, sehingga koneksi jaringan dapat memengaruhi pemuatan aset tersebut.

Cara kerja JavaScript — menghubungkan halaman dengan tindakan

JavaScript (JS) pada jobsheet berjalan di browser. Tag <script src="..."> memuat file, browser membaca perintahnya, lalu kode dapat mencari elemen HTML, mendengar event (klik, submit, ketikan), dan memperbarui tampilan. File umum ada di assets/js/app.js; file khusus seperti buku.js dan anggota.js menangani tabel masing-masing.

1. Tunggu DOM siap, lalu pasang event

document.addEventListener("DOMContentLoaded", function () {
    initTableFilter();
    initValidasiForm();
});

DOMContentLoaded berjalan setelah browser membentuk elemen HTML. Dengan menunggu event ini, pencarian selector seperti getElementById() tidak dijalankan terlalu dini. Fungsi inisialisasi biasanya memeriksa apakah elemennya ada; jika tidak ada di halaman tersebut, fungsi berhenti tanpa error.

2. Event menghubungkan aksi pengguna dan respons kode

Pola umumnya: pilih elemen dengan querySelector()/getElementById() → pasang addEventListener() → baca nilai atau elemen terkait → ubah hasil. Pada filter tabel, event keyup membaca kata pencarian, mengambil teks tiap baris, lalu menyembunyikan baris yang tidak cocok dengan mengatur row.style.display. Pada validasi form, event submit memeriksa field. Jika tidak valid, event.preventDefault() membatalkan pengiriman dan pesan error ditambahkan ke halaman.

3. Fetch API memuat JSON secara asinkron

Di Jobsheet 6, fungsi async menjalankan fetch("../data/buku.json"). await menunggu respons jaringan tanpa membekukan seluruh halaman; response.ok memastikan server berhasil, lalu response.json() mengubah teks JSON menjadi array/objek JavaScript. Program membuat baris tabel dan menambahkannya ke tbody. Bagian try/catch/finally menangani error dan selalu menyembunyikan indikator loading setelah selesai.

4. Batas perilaku front-end

Konfirmasi hapus yang hanya menjalankan row.remove() menghapus baris dari tampilan saat itu saja; ia tidak menghapus data di server atau database. Supaya perubahan tersimpan, tombol harus mengirim request ke handler PHP. Validasi JavaScript juga untuk kenyamanan pengguna saja: request dapat dibuat tanpa menjalankan JS, sehingga PHP tetap wajib memvalidasi input di server. Data eksternal sebaiknya dimasukkan dengan textContent atau di-escape, bukan digabung mentah ke innerHTML.

5. Interaksi yang dipakai di berbagai Jobsheet

  • Menu dan komponen Bootstrap: file JavaScript Bootstrap dari CDN mengaktifkan navbar collapse dan, pada Jobsheet 12, modal pembelian. Markup tombol menghubungkan komponen melalui atribut seperti data-bs-toggle dan data-bs-target.
  • Daftar statis/PHP: app.js memasang pencarian tabel dengan event input/keyup, mengonfirmasi aksi, mengatur menu seluler, dan memeriksa field tertentu pada form. Fungsi sering mengecek keberadaan elemen lebih dulu karena satu file JS dapat dipakai di beberapa halaman.
  • JSON di Jobsheet 6: buku.js dan anggota.js meminta file JSON dengan fetch(), menampilkan loading, mengecek status HTTP, membaca response.json(), lalu membuat baris tabel. Penanganan try/catch/finally menampilkan kegagalan dan merapikan status loading. Data diambil saat halaman daftar dibuka, bukan melalui tombol reload.
  • Formulir: event submit dapat memanggil preventDefault() saat validasi browser gagal. Jika lolos, Jobsheet statis belum tentu mengirim data ke server; pada Jobsheet PHP form dikirim melalui mekanisme HTML ke handler, bukan diubah menjadi AJAX oleh JS umum.

6. Batas dan pemeriksaan JavaScript

JS mengubah tampilan di browser, bukan sumber data permanen. Filter hanya menyembunyikan baris yang tidak cocok; menghapus baris dengan row.remove() tidak menghapus database. Pada Jobsheet PHP, aksi tersimpan bila tombol mengirim form ke handler server. Validasi HTML/JS dapat dilewati, jadi tetap validasi di PHP. Untuk pengujian, buka Developer Tools → Console/Network, cek apakah file JS dan JSON berhasil diminta, periksa selector elemen, respons HTTP, dan pesan error. Jangan memasukkan nilai pengguna ke innerHTML tanpa escaping; utamakan textContent atau encoding yang sesuai konteks.

Cara kerja PHP — memproses request di server

PHP dijalankan oleh web server (misalnya Apache/Laragon), bukan oleh browser pengguna. Ketika browser meminta file .php, server menjalankan kode PHP dan mengirim hasilnya—biasanya HTML—ke browser. Karena itu, pengguna melihat hasil halaman, bukan kode PHP mentah. Kode PHP dapat membuat halaman dari database, memeriksa login, atau menerima form.

1. Request GET dan POST

$_GET berisi nilai dari query URL, misalnya edit.php?id=7 untuk memilih rekaman. $_POST berisi data yang dikirim form dengan method="POST", lazimnya untuk menyimpan perubahan. Handler seperti proses_tambah.php membaca POST, memangkas spasi dengan trim(), memeriksa nilai, lalu memilih apakah menyimpan atau mengembalikan pengguna dengan redirect.

2. Validasi dan output aman

Validasi memastikan nilai sesuai aturan bisnis, misalnya nama wajib, harga angka dan tidak negatif, serta stok bilangan yang masuk akal. Validasi harus dilakukan di server karena nilai dari browser tidak dapat dipercaya. Saat menampilkan teks yang berasal dari pengguna/database ke HTML, helper e() memakai htmlspecialchars(..., ENT_QUOTES, 'UTF-8') agar karakter seperti < dan tanda kutip tidak ditafsirkan sebagai markup/script.

3. PDO dan prepared statement

$stmt = $pdo->prepare(
    "SELECT * FROM barang WHERE id = :id"
);
$stmt->execute(['id' => $id]);
$barang = $stmt->fetch(PDO::FETCH_ASSOC);

koneksi.php membuat objek PDO dari konfigurasi koneksi. prepare() menyiapkan SQL dengan placeholder; execute() mengirim nilai ID terpisah dari teks SQL; fetch() mengambil satu baris sebagai array. Prepared statement membantu mencegah nilai masukan diperlakukan sebagai bagian dari perintah SQL. Halaman list.php biasanya memakai fetchAll() untuk mengambil banyak rekaman lalu mengulanginya dengan foreach.

4. Session, flash message, dan redirect

session_start() membuka data session milik browser yang disimpan di sisi server. Session dipakai untuk status login dan pesan singkat antar-request. Handler menyimpan misalnya $_SESSION['flash'], lalu mengirim header Location untuk mengarahkan browser ke halaman daftar. Halaman tujuan membaca dan menampilkan pesan tersebut. Setelah mengirim header redirect, exit menghentikan proses agar kode berikutnya tidak ikut dijalankan.

5. PDO transaction, autentikasi, dan CSRF

beginTransaction() membuka satu rangkaian perubahan database; commit() menyimpan semuanya; rollBack() membatalkan semuanya bila terjadi kegagalan. Ini penting untuk proses seperti pembelian: kurangi stok dan catat transaksi harus sama-sama berhasil. auth.php memeriksa identitas pada session sebelum halaman terbatas ditampilkan. Token CSRF dibuat dan disimpan di session, dimasukkan sebagai field tersembunyi dalam form, lalu diverifikasi oleh handler POST untuk memastikan form berasal dari sesi halaman yang sah.

Ringkas alur server: browser mengirim request → PHP memeriksa login/CSRF dan validasi → PHP membaca/menulis database dengan PDO → PHP menyimpan flash message bila perlu → PHP mengirim halaman atau redirect → browser merender HTML dan CSS, kemudian JavaScript mengaktifkan interaksi.

6. Halaman PHP, template bersama, dan sumber data

Halaman PHP dapat menjalankan logika sebelum mengeluarkan HTML: memuat koneksi/helper, membaca query/form, mengambil data, lalu menyisipkan nilai ke template. include/require menyatukan header/footer supaya navbar, CSS, JavaScript, dan footer tidak perlu ditulis ulang di setiap halaman. Handler memproses data lalu biasanya melakukan redirect; halaman daftar berikutnya menjalankan SELECT dan merender ulang HTML dari hasil database. Jobsheet 7 berbeda: daftar dibentuk dari array session, bukan PDO. Jobsheet 1–6 adalah HTML/JavaScript sisi browser tanpa pemrosesan database PHP.

7. CRUD, form, dan alur request

Create: halaman tambah.php menampilkan form dan handler proses_tambah.php melakukan validasi lalu INSERT. Read: list.php menjalankan SELECT, mengambil satu/banyak baris dengan fetch()/fetchAll(), lalu mengulanginya menggunakan foreach. Update: halaman edit.php?id=... mengambil ID via GET, menampilkan nilai awal dan mengirim form; handler melakukan UPDATE untuk ID tersebut. Delete: handler menghapus rekaman. GET lazim untuk membaca/memfilter halaman; POST digunakan untuk mengirim perubahan. Pada versi awal Jobsheet 8–10 beberapa aksi hapus menggunakan GET; mulai versi pengamanan Jobsheet 11, aksi tertentu memakai POST dan CSRF. Jangan menyimpulkan semua handler di setiap versi menggunakan metode atau perlindungan yang sama.

8. Validasi, error, escaping, dan SQL

Nilai dari form diperlakukan sebagai input yang belum dipercaya. PHP memeriksa field wajib, angka, rentang, dan ID sebelum query. PDO memakai placeholder dan parameter pada prepare()/execute(); hindari menyambung nilai pengguna langsung ke SQL. Saat menghasilkan HTML, e() pada Jobsheet 11–12 membungkus htmlspecialchars() untuk mengodekan karakter khusus. Handler dapat menyimpan pesan sukses/gagal ke session dan menampilkan kembali sebagai flash message; exception PDO atau business rule yang gagal perlu ditangani sesuai alur yang dibuat handler.

9. Session, autentikasi, dan izin akses

session_start() membuka/melanjutkan sesi browser. Jobsheet 7 menyimpan data perpustakaan sementara di $_SESSION; Jobsheet 8–9 memakai session terutama untuk flash message; Jobsheet 10–12 juga menyimpan identitas user dan role. Registrasi meng-hash password dengan password_hash(), login memverifikasinya lewat password_verify(), dan helper auth mengalihkan pengunjung yang belum login. Login dapat memperbarui session ID dan fitur “Ingat Saya” membaca cookie sesuai implementasi tiap Jobsheet. Autentikasi (siapa yang masuk) berbeda dari otorisasi (aksi apa yang boleh dilakukan); pemeriksaan role hanya berlaku pada handler/halaman yang benar-benar mengeceknya.

10. CSRF, transaksi database, dan penguncian stok

Jobsheet 11–12 menyediakan csrf_token(), csrf_field(), dan csrf_verify(). Token tersimpan di session, dikirim sebagai hidden input, lalu dibandingkan dengan nilai POST memakai hash_equals(). Perlindungan hanya berlaku saat form menyertakan token dan handler memanggil verifikasi. Pada alur pembelian, transaksi PDO menyatukan perubahan stok dan pencatatan kas; pada Jobsheet 12 SELECT ... FOR UPDATE mengunci baris barang selama stok diperiksa/diperbarui agar pembelian bersamaan tidak memakai stok yang sama. Foreign key dan JOIN di Jobsheet 12 menyimpan serta membaca hubungan transaksi dengan barang/pelanggan; skema ini berbeda dari catatan teks di Jobsheet 8–11.

11. Cara menelusuri dan menguji PHP

Ikuti satu halaman dari form (atribut method/action) ke handler, lalu ke query, perubahan session/flash, redirect, dan halaman tujuan. Pastikan PHP dijalankan melalui server web; membuka file PHP sebagai file:// tidak mengeksekusi PHP. Untuk database, pastikan PostgreSQL aktif, skema Jobsheet yang tepat sudah dibuat, kredensial/environment variable benar, dan ekstensi PDO PostgreSQL tersedia. Uji input valid dan tidak valid, perubahan sebelum/sesudah, akses tanpa login, token kosong/salah pada handler yang dilindungi, serta pembelian dengan stok cukup maupun tidak cukup. Browser Network/response dan log PHP membantu membedakan masalah routing, syntax, koneksi database, validasi, serta query.

Jobsheet 1 — struktur HTML

Latihan awal membentuk prototipe SIMPUS dengan HTML statis. Angka ringkasan dan baris tabel adalah contoh yang ditulis langsung di dokumen, belum diambil dari penyimpanan data.

  • index.html: header dan navigasi, bagian sambutan, tiga kartu ringkasan (buku, anggota, pinjaman), serta footer.
  • buku/list.html dan anggota/list.html: tabel contoh untuk memperlihatkan daftar buku/anggota. Tombol aksi hanya tampilan; pada tahap ini belum mengubah data.
  • buku/tambah.html dan anggota/tambah.html: formulir input dengan label dan field yang sesuai jenis data.

Tag seperti header, nav, main, section, table, form, dan footer memberi struktur semantik. Tautan href menghubungkan halaman-halaman tersebut.

Jobsheet 2 — CSS terpisah

Halaman SIMPUS dari tahap sebelumnya tetap statis, tetapi kini memanggil assets/css/style.css. File CSS menerapkan gaya dasar pada body, header/menu, konten, kartu ringkasan, tabel, form, dan footer.

Selector seperti header, table, atau form memilih elemen HTML; deklarasi seperti color, padding, dan background-color menentukan tampilannya. Hubungan HTML dan CSS terjadi melalui tag link di bagian head. Data dan tombol tetap belum dinamis.

Jobsheet 3 — Bootstrap dan CSS kustom

Struktur tetap berupa halaman statis buku dan anggota. assets/css/style.css mengatur warna, jarak, kartu, serta layout daftar/ringkasan. Meta viewport membantu halaman menyesuaikan lebar layar. Halaman daftar dan form memiliki navigasi yang sama.

Bootstrap 5 dimuat melalui CDN lalu disesuaikan dengan CSS kustom. Baris tabel, angka ringkasan, dan form masih ditulis di HTML; tombol Edit/Hapus belum menyimpan perubahan. File docs/wireframe.md menjelaskan rancangan antarmuka yang menjadi acuan halaman. Di browser, Bootstrap menyediakan komponen dan grid siap pakai, sedangkan assets/css/style.css menambahkan identitas visual proyek. Perubahan data belum tersambung ke server.

Jobsheet 4 — konsistensi halaman dan wireframe

Folder ini melanjutkan pola HTML + CSS dari Jobsheet 3. index.html, halaman buku, dan halaman anggota membentuk halaman statis yang saling terhubung dengan tautan relatif. assets/css/style.css menjadi sumber gaya bersama sehingga perubahan tema dapat diterapkan ke semua halaman.

Navbar seluler memakai checkbox dan CSS untuk membuka menu. Tidak ada halaman login pada Jobsheet 4. docs/wireframe.md berisi rancangan antarmuka dan Infografis.png adalah bahan visual; keduanya tidak dieksekusi seperti HTML atau CSS.

Jobsheet 5 — Bootstrap dan dasar JavaScript

Halaman SIMPUS menggunakan Bootstrap melalui CDN untuk navbar, grid, kartu, tombol, tabel, dan form; assets/css/style.css menambahkan gaya proyek. Meta viewport dan komponen Bootstrap membantu tampilan menyesuaikan layar.

  • index.html, halaman di buku/ dan anggota/: halaman beranda, daftar, dan formulir yang berpindah dengan tautan. Navbar hanya menampilkan tautan daftar buku dan daftar anggota; tautan tambah tetap tersedia pada halaman formulir/daftar.
  • Halaman login tidak ada di Jobsheet 5.
  • assets/js/app.js: perilaku sisi browser seperti toggle menu, konfirmasi aksi, filter tabel, dan validasi isian jika elemen terkait tersedia.

Bootstrap JavaScript dipanggil untuk komponen interaktif Bootstrap, misalnya tombol navbar. Belum ada backend yang menyimpan data permanen pada tahap ini.

Jobsheet 6 — data JSON dan fetch

Daftar buku dan anggota kini dirender dari file JSON melalui JavaScript, bukan seluruhnya ditulis sebagai baris tabel tetap.

  • data/buku.json dan data/anggota.json: contoh rekaman dalam format array JSON.
  • assets/js/buku.js dan anggota.js: fungsi async memakai fetch() untuk meminta JSON, mengubah respons menjadi objek, membuat elemen baris, dan memasukkannya ke tbody. Indikator loading ditampilkan selama proses; kegagalan request ditampilkan sebagai pesan pada tabel.
  • assets/js/app.js: fitur umum seperti pencarian, konfirmasi, menu, atau validasi form. Pemuatan data terjadi otomatis saat halaman daftar dibuka; tombol muat ulang terpisah sudah tidak digunakan.
  • Halaman HTML menyediakan wadah tabel, label pencarian, indikator loading, dan tautan ke skrip yang mengisinya.

JSON pada tahap ini adalah data contoh yang dibaca browser. Fetch dari file lokal biasanya perlu dijalankan lewat web server lokal, bukan dibuka sebagai file://.

Jobsheet 7 — PHP, session, dan form POST

Aplikasi berpindah dari halaman HTML statis ke PHP. index.php, halaman daftar/form di buku/ dan anggota/, serta includes/header.php/footer.php membentuk tampilan server-rendered. CRUD pada tahap ini menyimpan data di array $_SESSION, bukan di JSON atau database.

  • buku/list.php dan anggota/list.php menyusun tabel dari data session. tambah.php menampilkan form, sedangkan proses_tambah.php memeriksa request, memvalidasi nilai, menangani tambah/edit/hapus, menyiapkan pesan flash, lalu redirect ke daftar.
  • Halaman login tidak ada pada Jobsheet 7; autentikasi baru diperkenalkan di Jobsheet 10.
  • assets/js/app.js dan assets/css/style.css mendukung interaksi browser dan tampilan antarmuka.
  • data/*.json dan docs/wireframe.md tersedia sebagai berkas data contoh/rancangan; JSON tersebut tidak menjadi penyimpanan CRUD. Saat form dikirim, PHP memperbarui array session dan daftar membaca ulang array tersebut pada request berikutnya. Karena itu, data tersedia hanya selama session yang sama masih aktif dan tidak bertahan sebagai rekaman permanen di database.

Session menyimpan data sementara antar-request bagi sesi browser. Data dapat diakses selama cookie session yang sama dipakai; memulai sesi baru tidak memuat data sesi sebelumnya. Session bukan penyimpanan permanen seperti database.

Jobsheet 8 — awal aplikasi inventaris dan penjualan

Mulai tahap ini proyek berpindah dari SIMPUS ke aplikasi Toko Madura. Data tidak lagi ditulis tetap di HTML atau disimpan dalam session: PHP berkomunikasi dengan PostgreSQL memakai PDO. Modul ini menjadi dasar untuk mengelola barang, pelanggan, stok, dan catatan kas.

Konfigurasi dan skema

  • includes/koneksi.php membaca PGHOST, PGPORT, PGDATABASE, PGUSER, dan PGPASSWORD, lalu membuat objek $pdo. Jika environment variable tidak tersedia, file menyediakan default koneksi lokal yang perlu disesuaikan dengan database di komputer.
  • sql/barang_pelanggan_transaksi.sql membentuk tiga tabel: barang menyimpan nama, produsen, tanggal masuk (kolom tahun), kode, harga, stok, dan kategori; pelanggan menyimpan identitas/kontak; transaksi mencatat jenis kas, nominal, keterangan, dan tanggal. Pada tahap ini transaksi masih berupa catatan teks; belum ada kolom relasi ID barang/pelanggan.
  • Sebelum mencoba halaman, siapkan PostgreSQL dan database, jalankan skema SQL Jobsheet 8, lalu atur kelima environment variable koneksi atau sesuaikan nilai default lokal dalam includes/koneksi.php. Pastikan ekstensi PDO PostgreSQL aktif di PHP. Setelah server lokal diarahkan ke folder proyek, buka Jobsheet8/index.php; jika koneksi gagal, periksa nama database, kredensial, host/port, dan apakah layanan PostgreSQL sudah berjalan.

Alur halaman dan perubahan data

  • index.php menampilkan ringkasan barang, pelanggan, pemasukan/pengeluaran bulan berjalan, peringatan stok rendah, dan transaksi terakhir.
  • barang/list.php dan pelanggan/list.php membaca rekaman untuk tabel. Pasangan tambah.php dan proses_tambah.php menampilkan form, memvalidasi nilai di sisi server, lalu memakai prepared statement untuk menambahkan rekaman.
  • barang/proses_tambah.php juga membuat catatan pengeluaran modal awal berdasarkan harga dikali stok. barang/proses_keluar.php mengurangi stok barang dan mencatat pemasukan penjualan; pelanggan/proses_beli.php memeriksa pelanggan/barang/stok, mengurangi stok, dan mencatat pembelian pelanggan. Perubahan stok dan catatan kas pada kedua alur dibungkus transaksi database.
  • includes/header.php/footer.php membagi layout bersama, sedangkan assets/css/ dan assets/js/ mengatur tampilan dan interaksi browser seperti menu, filter tabel, konfirmasi, atau validasi sisi klien.

Cara memahami dan menguji alurnya

Ikuti satu form dari halaman tambah.php ke atribut action, lalu ke handler proses_*.php: handler membaca $_POST, memvalidasi, menyiapkan SQL, mengikat parameter dengan prepare()/execute(), menyimpan pesan flash di session, lalu redirect. Uji dengan menambah barang berstok tertentu, cek apakah barang dan catatan pengeluaran muncul, lalu lakukan barang keluar atau pembelian dengan jumlah yang tersedia. Ulangi dengan jumlah melebihi stok dan pastikan pembelian ditolak serta stok tidak berubah.

Struktur utama Jobsheet 8: index.php untuk dashboard; barang/ dan pelanggan/ untuk daftar, form, dan handler; includes/ untuk koneksi/layout; assets/ untuk CSS/JavaScript; serta sql/ untuk skema database. Belum ada login/otorisasi. Transaksi belum menyimpan foreign key; keterkaitan hanya ditulis sebagai teks keterangan.

Jobsheet 9 — melengkapi CRUD inventaris

Jobsheet 9 melanjutkan pola PDO dan tabel dari Jobsheet 8. Fokus tambahannya adalah membaca satu rekaman untuk diedit, mengirim nilai baru, memperbaruinya di database, dan menghapus rekaman. Dengan demikian pengelolaan master barang/pelanggan mencakup CRUD: Create, Read, Update, dan Delete; transaksi stok dan pembelian tetap tersedia.

  • barang/edit.php dan pelanggan/edit.php mengambil ID, menjalankan SELECT dengan prepared statement, lalu menampilkan nilai yang ada pada form. Form mengirim ID dan nilai baru ke handler dengan POST.
  • barang/proses_edit.php dan pelanggan/proses_edit.php memvalidasi data, kemudian menjalankan UPDATE ... WHERE id = :id. barang/list.php/pelanggan/list.php menyediakan daftar beserta tautan aksi.
  • barang/hapus.php dan pelanggan/hapus.php memakai transaksi database; implementasi Jobsheet 9 menghapus catatan transaksi lama dengan mencocokkan teks pada kolom keterangan sebelum menghapus master. Karena pencocokan berdasarkan teks/nama, cara ini merupakan pendekatan latihan yang rapuh—bukan relasi data yang kuat; perubahan relasional diperkenalkan di Jobsheet 12.

Skenario uji yang disarankan

Tambahkan satu barang dan satu pelanggan, ubah nama atau harga melalui form edit, lalu buka kembali daftar untuk memastikan nilai tersimpan di database. Hapus data uji dan periksa dampak penghapusan pada catatan yang dikaitkan melalui keterangan. Coba simpan form dengan field wajib kosong untuk melihat validasi serta pesan flash. Struktur pentingnya adalah pasangan halaman edit.php/proses_edit.php untuk pembaruan, hapus.php untuk penghapusan, serta list.php sebagai titik masuk aksi. Query edit menggunakan ID untuk membatasi rekaman yang diperbarui; validasi harus diperiksa lagi di PHP karena validasi HTML/JavaScript dapat dilewati.

Jobsheet 10 — registrasi, login, dan session

Jobsheet 10 menambahkan autentikasi ke aplikasi inventaris. Halaman di auth/ menyediakan form login/registrasi; handler memeriksa kredensial atau membuat akun; includes/auth.php menjadi guard yang mengecek $_SESSION['user_id'] dan mengalihkan pengunjung yang belum masuk. Halaman/aksi terbatas perlu menyertakan guard agar pemeriksaan benar-benar berlaku.

  • auth/proses_register.php memeriksa nama, username, panjang password minimum enam karakter, dan username duplikat. Password disimpan sebagai hash menggunakan password_hash(), bukan teks biasa; saat login password_verify() membandingkan password yang dikirim dengan hash. Skema akun ada di sql/user.sql.
  • Setelah login sukses, ID, nama, dan role dimasukkan ke session. Logout mengakhiri sesi dan menghapus cookie remember_user jika ada. Navbar menampilkan Login saat anonim dan Logout ketika session aktif.
  • Checkbox “Ingat Saya” menyetel cookie remember_user selama 30 hari. Guard memakai ID dari cookie untuk memulihkan session dari tabel users. Percobaan login gagal dihitung di session per username dan akses login ditolak setelah tiga kegagalan pada sesi/perangkat tersebut.

Memeriksa perilaku login

Jalankan skema akun, daftarkan akun uji, pastikan nilai kolom password adalah hash, lalu login dengan password benar dan salah. Buka halaman yang dilindungi sebagai pengunjung anonim untuk memeriksa redirect, lalu logout. Uji “Ingat Saya” dengan menutup lalu membuka kembali browser hanya jika sesi/cookie tetap tersimpan.

Struktur modul: auth/ berisi login, registrasi, logout, dan handler; includes/auth.php memulihkan/memeriksa identitas session; sql/user.sql membuat tabel akun. Ini adalah implementasi pembelajaran, bukan rancangan autentikasi produksi: cookie remember menyimpan ID user secara langsung dan belum memakai token acak yang dapat dicabut; jumlah percobaan login disimpan di session; helper guard memeriksa login, bukan otorisasi role per halaman.

Jobsheet 11 — output aman dan perlindungan CSRF

Jobsheet 11 meneruskan login dan CRUD dari Jobsheet 10 dengan helper output serta token CSRF. Tujuannya membedakan tiga pemeriksaan yang sering tercampur: autentikasi memastikan pengguna sudah login; otorisasi memeriksa hak akses tertentu; token CSRF membantu memastikan aksi POST berasal dari form/sesi yang memegang token yang benar.

  • includes/helpers.php menyediakan e(), pembungkus htmlspecialchars() dengan UTF-8 dan escaping tanda kutip, untuk menampilkan nilai dinamis sebagai teks HTML.
  • includes/csrf.php: csrf_token() membuat token acak dan menyimpannya di session; csrf_field() menghasilkan input tersembunyi untuk form; csrf_verify() membandingkan nilai POST dengan token session memakai hash_equals() dan menolak request tidak valid dengan HTTP 403.
  • Form yang dilindungi harus menyertakan csrf_field(), dan handler yang memprosesnya harus memuat helper lalu memanggil csrf_verify(). Pada aksi hapus barang, misalnya, implementasi juga mensyaratkan POST dan memeriksa role admin. Jangan menganggap token otomatis melindungi semua endpoint: perlindungan berlaku pada form/handler yang benar-benar memasang kedua sisi tersebut.
  • includes/auth.php, file SQL, header/footer, CSS, dan JavaScript melanjutkan fungsi yang sudah ada. Tombol aksi hapus pada daftar memakai form POST, bukan sekadar tautan GET.

Skenario uji keamanan dasar

Login, buka form yang memiliki token, lalu kirim secara normal untuk memastikan aksi tetap berjalan. Kirim POST tanpa token atau dengan token yang diubah dan pastikan respons ditolak; coba buka handler hapus menggunakan GET dan pastikan tidak ada penghapusan. Masukkan teks seperti <script> ke nilai yang ditampilkan, lalu periksa bahwa nilai dirender sebagai teks, bukan dieksekusi.

Cakupan token ditentukan per aksi: form harus menyisipkan csrf_field() dan handler terkait harus memanggil csrf_verify(). Terapkan pengujian token salah/kosong hanya pada alur yang memasang keduanya; halaman atau endpoint lain tidak otomatis terlindungi hanya karena file helper tersedia. Escaping output dengan e() juga perlu dipakai saat mencetak nilai yang dapat berasal dari pengguna.

Jobsheet 12 — transaksi relasional dan konsistensi stok

Jobsheet 12 mengubah transaksi dari catatan teks Jobsheet 8–11 menjadi data relasional. Berkas skema sql/barang_pelanggan_transaksi.sql menambahkan pelanggan_id, barang_id, dan jumlah pada tabel transaksi. ID pelanggan dan barang menjadi foreign key dengan ON DELETE SET NULL: jika master dihapus, baris transaksi dan nominalnya tetap ada, sementara referensi yang dihapus menjadi NULL.

Alur pembelian dan penjagaan stok

  1. pelanggan/proses_beli.php memvalidasi ID pelanggan/barang dan jumlah pembelian, lalu memulai transaksi PDO.
  2. Handler membaca pelanggan dan mengambil baris barang menggunakan SELECT ... FOR UPDATE. Kunci baris menahan pembelian bersamaan agar tidak sama-sama menghitung dari stok lama.
  3. Jika data ditemukan dan stok cukup, handler mengurangi stok lalu menyimpan penjualan sebagai baris transaksi dengan ID barang, ID pelanggan, jumlah, nominal, jenis, dan tanggal.
  4. commit() menyimpan pengurangan stok dan catatan penjualan bersama-sama. Jika proses gagal, rollBack() membatalkan perubahan yang sudah dilakukan dalam transaksi tersebut.

Riwayat, dashboard, dan pengujian

  • transaksi/riwayat.php menerima filter pelanggan melalui GET dan memakai LEFT JOIN untuk membaca nama barang pada transaksi pelanggan terpilih. LEFT JOIN mempertahankan baris transaksi saat referensi barang kosong.
  • index.php menggunakan relasi untuk menampilkan ringkasan dan transaksi terbaru beserta data master terkait. Header menampilkan menu riwayat untuk pengguna yang sudah login.
  • Siapkan database sesuai skema Jobsheet 12 sebelum menguji—struktur transaksi ini lebih lengkap daripada tabel transaksi pada Jobsheet 8. Buat pelanggan dan barang uji, lakukan pembelian dengan stok cukup, lalu periksa stok, transaksi, dashboard, dan riwayat pelanggan. Coba jumlah melebihi stok: proses harus gagal tanpa mengurangi stok atau meninggalkan catatan penjualan. Untuk memahami aturan hapus, hapus master uji yang terkait dan periksa bahwa baris transaksi tetap tersimpan dengan referensi kosong.

Inti pelajaran: foreign key menyimpan hubungan menggunakan ID, JOIN menyatukan data untuk laporan, transaksi database menjaga beberapa perubahan tetap atomik, dan FOR UPDATE melindungi stok pada pembelian bersamaan. Untuk setup lokal, gunakan definisi tabel dalam sql/barang_pelanggan_transaksi.sql dan pastikan skema Jobsheet 12 diterapkan pada database yang dipakai aplikasi. Periksa struktur transaksi yang ada sebelum menjalankan skema pada database berisi data penting karena file SQL mendefinisikan tabel transaksi tahap ini.
